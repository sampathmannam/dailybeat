# Security and reliability review — 21 September 2026

Base: `3c415a8` (DailyBeat 4.3.3). This review covers the Android application, optional cloud
clients, restore boundaries, capture durability, generated documents, and the existing backend
authorization controls. It does not change the database schema, production backend, signing
identity, or published release. No production account or personal history was used for testing.

## Findings and corrections

| Boundary | Verified problem | Correction and regression evidence |
|---|---|---|
| Backup restore / AI credentials | A restored provider URL and enabled flag could direct a device's existing API key and future journal requests to a different server. Legacy backup contents lack client authentication. | Preserve this phone's provider/model/address, disable Cloud AI after every restore, and require fresh consent. `LocalBackupStoreTest`. |
| Authentication concurrency | A delayed sign-in/refresh could repopulate credentials after sign-out. Concurrent callers could rotate the same refresh token. | Serialize refresh, check session generation and account identity before persisting responses; sign-out/new sign-in takes precedence. `SupabaseBackupClientTest`. |
| Queued cloud requests | A queued request retained old consent, destination and API-key values. Coroutine cancellation left blocking network reads running. | Recheck settings and credentials at transmission, cancel the HTTP call with its coroutine, reject credential-bearing/ambiguous compatible URLs and unknown providers, enforce redirect refusal even for injected clients. `CloudLlmClientAdversarialTest`. |
| Document privacy | Generated PDFs/ZIPs and audit files used app-specific external storage; FileProvider covered more than completed exports. Reused PDF filenames let an older URI grant expose a later document. | Use internal storage, share only the exports directory, keep logs/staging outside it, and assign unique export names. Preserve completed legacy exports during migration. `PrivateStorageHardeningTest`. |
| Erasure and migration | Cleanup missed alternate historical output roots and interrupted export files; filesystem links could escape cleanup boundaries. | Sweep known app-owned roots/staging without following links. Serialize migration with erase/restore; preserve originals on migration failure. `PrivateStorageHardeningTest`. |
| Delayed writes after erase/restore | AI generation, voice transcription and retained editor drafts could finish after erasure and recreate private records, or overwrite a restored history. | Introduce a separate local-data generation, invalidate it during erase/successful restore, and verify it under the storage mutex at final saves/exports. Share previews carry this generation. New network waits do not hold the storage mutex; tracking pause and failed restore leave editing intact. `ReportDataReplacementTest`, `VoiceCaptureDataReplacementTest`, `CaptureDataGenerationTest`, `DiaryDataReplacementTest`, `DiaryShareServiceTest`. |
| Capture input | NaN GPS values could abort a whole SQLite batch. A future timestamp could poison monotonic checkpoints and block later fixes. | Validate before insertion; reject future timestamps and ignore impossible persisted checkpoints/future breadcrumbs when resuming. Preserve finalized records. `CaptureProcessorTest`, `LocationQualityFilterTest`. |
| Capture privacy | A quick pause/resume could make an old queued callback appear valid again. Stop/recovery could continue network enrichment from an earlier eligibility snapshot. | Invalidate callback generations on privacy changes, recheck permissions, flush stop data locally, and recheck current capture consent before each geocoder request. `CapturePrivacyEpochTest`, `GeocodingConsentTest`, `CaptureProcessorTest`. |
| Numeric stability | Near-antipodal coordinates can round the Haversine intermediate above one, yielding NaN and bypassing a speed comparison. | Clamp the intermediate and reject non-finite derived speed; exercise an antipodal one-second jump. `LocationQualityFilterTest`. |
| Untrusted source metadata | An imported event type could inject citation IDs/new lines, causing source-reference expansion and excessive allocation. | Sanitize event types, derive IDs from bounded source lines, validate citation ranges directly, and bound correction violations. `DayContextBuilderTest`, `ReportIntegrityValidatorTest`. |
| Diagnostic input | A corrupted log containing one huge line could force an unbounded line read. | Read a bounded byte tail before splitting lines. `BoundedLogLinesTest`. |

## Verification

- Repository policy/tests: 116 passed.
- Gitleaks: 319 Git commits scanned, no leaks reported. Local untracked output folders are not
  evidence of the contents of the shipped application and were not included in changes.
- Trivy with refreshed vulnerability data: zero high/critical findings in the existing resolved
  standard and FOSS dependency inventories. No runtime dependency was changed by this patch.
- GitHub Dependabot: no open alerts at review time.
- Pre-final standard Android pass: 397 unit tests, zero failures/errors, one store-only test skipped;
  debug APK, instrumentation APK and lint succeeded. This pass predates the final erase/restore
  race regressions. Final validation is tracked separately in the associated pull request's check
  runs and handover; this intermediate result is not a claim that those later tests passed.

The audit was cross-reviewed by separate coding agents. This improves defect detection but is not
an independent professional penetration test. The review categories follow
[OWASP MASVS](https://mas.owasp.org/MASVS/) and
[Android security guidance](https://developer.android.com/privacy-and-security/security-best-practices).

## Remaining operational limits

- No claim of being unhackable or enterprise-certified is made. A rooted/compromised operating
  system or an attacker controlling an unlocked device is outside the app sandbox guarantee.
  Local journal data still relies on Android private storage and device encryption; this patch
  does not introduce database encryption or an additional app authentication screen.
- Sent network data and files accepted by another app cannot be recalled. Disconnected removable
  storage cannot be erased while unavailable. Failed migration/erasure is reported rather than
  silently claimed successful; invalidated encrypted preferences may require device recovery.
- Existing cloud backups are separate copies. This patch neither deletes legacy plaintext
  backups nor changes backend retention. Supabase production auth/rate limits, service-role access,
  recovery operations, and incident ownership require ongoing operator review.
- Capture rejects observable malformed/mock fixes but cannot establish the authenticity of every
  location supplied by the OS. A discarded corrupt checkpoint cannot reconstruct missing history.
  Battery cost, OEM process survival, and real stop recall require physical-device trials.
- Store acceptance, contractual security requirements, penetration testing and operational SLAs
  remain external acceptance work. The existing incident/recovery runbook still applies.
