# Security and reliability review — 24 September 2026

Base: `7057b5ea44bdba12ef7224342afee17d3264f2f1`, version 4.3.5 (39).
This working-tree review preserves the existing place-label/replay fixes and phone design.
It does not publish an update, change signing keys, or operate on a personal journal.

## Corrections

| Boundary | Failure addressed | Protection / regression coverage |
|---|---|---|
| Review and saved places | Retained screens could recreate erased titles/places or edit a restored row with a reused ID. Privacy updates could overwrite a newer place name. | Check the original data generation under the storage lock, compare the full current row, and atomically save learned places plus corrections. Review, repository, Settings, and Days regression tests. |
| Retained UI | Feed/search/insights caches and naming/sharing dialogs could retain erased records. Unknown destinations could become a fabricated recurring-place pattern. | Clear/reload on data replacement, bind drafts to the loaded generation, dismiss private dialogs, and exclude unavailable labels from recurring-place analysis. Three Android UI regressions use synthetic data. |
| Credentials and privacy choices | Queued saves/authentication could survive erasure or sign-out. Waiting for the storage lock could delay a privacy-off action or let an earlier enable undo it. | Generation-checked key/config writes and authentication, immediate consent withdrawal, revision-checked queued enables, cancellable connection jobs, and stale-confirmation rejection. Preserve newer drafts and show empty-form validation. |
| Automatic reports | A queued retry could run after automatic reports were disabled; late generation could still append a report. | Cancel only automatic report work, check current consent at execution and final save, and preserve explicitly requested manual generation. |
| Restore intent and partial failures | A download begun before erasure or another restore could overwrite newer local state. A preference failure after records committed could lose its error message. | Carry the original generation through every restore format and check it inside the final apply lock. A typed partial-restore error truthfully distinguishes committed records from failed settings and only appears for the still-current restore. Delayed-download, queued-apply and preference-fault regressions. |
| Backup transport and size | Cancellation left blocked HTTP reads alive. Injected clients could follow redirects. Less-compressible pages and PostgreSQL JSONB formatting could exceed server payload limits despite valid plaintext/compact JSON sizes. | Cancellable bounded HTTP transport, redirect refusal, bounded abandoned-upload cleanup, and splitting at record boundaries using plaintext, wire and canonical server-byte limits. Exact per-part and cumulative boundary regressions; existing restore ceilings preserved. |
| Capture recovery | Interrupted shutdown could leave an open stop across a privacy pause. A failed final flush could survive a quick re-enable. | Recover offline when capture is unavailable and persist the existing suspended-checkpoint boundary after draining queued observations, before final flush. A final-transaction fault regression checks the rapid-resume path. If storage fails before the boundary itself can persist, durable recovery cannot be guaranteed. |
| Geocoding | Late responses could cache enrichment after consent changed; wall-clock rollback could extend request spacing for hours. | Recheck consent/endpoint, cancel the socket with its coroutine, and use bounded monotonic request spacing. |
| External JSON | Byte limits alone did not prevent deeply nested provider responses or backup data from overflowing recursive JSON parsing. | Strict iterative nesting validation before recursive parsing at geocoding, cloud-response, generated-event and backup/import entry points. Preserve existing byte caps and controlled error handling. |
| Offline dark maps | Published cartography had low-contrast road labels and streets. | Adjust only dark paint in memory; test actual package colours, retain geometry/URLs/layout/light mode, and verify immutable resource hashes remain unchanged. Native rendering uses the same production helper. |
| Backend archive publication | SQL NULL comparison allowed a missing page count to bypass completeness checks for the caller's own archive. | An additive migration explicitly rejects null/out-of-range counts. The new regression fails on the old schema and passes after migration. Owner-only permissions remain unchanged. |

### Test failures investigated, not discarded

- The first Android 16 instrumentation launch hit an ANR before executing tests. The saved
  trace was in DEX verification under `ActivityThread.initInstrumentation`; normal app cold
  start succeeded. Precompiling both disposable test packages outside the runner's startup
  deadline resolved it. This failed attempt is retained separately from the successful run.
- An earlier full Android 16 run timed out waiting for the Review completion action to exist
  in the semantics tree before scrolling. The same flow passed in isolation. The test now
  scrolls the virtualised list while awaiting the new action and still asserts its visible
  label and the completed Days card. The final full suite passes without dropping the test.
- The complete-state map activation/deletion fixture is not supplied. Its skip is not counted
  as a pass. `CloudBackupLiveTest` is deliberately excluded; no production credentials or
  personal cloud backups are exercised.

## Scope and operational limits

- Only disposable `com.dailybeat.app.qa.e2eloop` installations and synthetic data are used.
  The connected physical phone and the user's unrelated emulator are not modified.
- Backend SQL is exercised on fresh isolated PostgreSQL 16.14 with pgTAP 1.3.4 and
  synthetic Auth roles. The historical schema first reproduced all eight prior fingerprints.
  This is not a live GoTrue/PostgREST or production-backup test.
- Instrumented runtime tests use debug QA packages. The optimised unsigned release APK is
  built and package-checked, not installed on the user's phone or published as an update.
- `202609240001_archive_publish_count_validation.sql` is **not applied to production**.
  The schema baseline explicitly identifies its unreleased local verification state.
- Existing platform protections were reviewed: internal export-only FileProvider, disabled
  Android backup/device transfer, narrowly exported components, TLS/redirect boundaries,
  bounded map downloads/ZIP extraction, reviewed sharing copies, and pinned dependencies.
- No claim of zero latent bugs, being unhackable, certification, or an independent professional
  penetration test is made. Rooted/compromised devices and copies already accepted by another
  app/provider remain outside the app's recall or sandbox guarantees.
- Physical battery drain, GPS venue accuracy, OEM background survival, all-device compatibility,
  store acceptance, production migration state and live-account recovery need their respective
  controlled field/deployment checks. A cancelled request cannot recall data already sent.
- Journal storage still relies on Android private storage and device encryption; this patch
  does not introduce whole-database encryption or an additional app lock.
- Existing lint advisories are not erased or suppressed to produce a clean-looking report.
  They include Kotlin convenience APIs, dependency upgrade suggestions, plural resources and
  resource housekeeping. The two `ImplicitSamInstance` reports point to explicit Android
  `Context.stopService(Intent)` calls, not listener-removal callbacks. Synchronous map preference
  commits deliberately provide durable activation/deletion ordering. These are documented
  separately from executable test failures and do not establish zero technical debt.

Review categories follow [OWASP MASVS](https://mas.owasp.org/MASVS/) and
[Android security guidance](https://developer.android.com/privacy-and-security/security-best-practices).
Impeccable's hardening guidance informed stale-dialog handling, actionable errors and dark-map
readability; it did not change the app's chosen yellow, carbon theme or navigation design.
